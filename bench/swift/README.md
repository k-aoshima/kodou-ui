# Swift のベンチ

Web のベンチ（`bench/`）と同じ画面を、macOS のネイティブで作り方を変えて比べます。Kodou-ui の決まりを Swift に移したときに、軽さが残るかを確かめるためのものです。

## 比べる版

画面は Web のベンチと同じです。1 万行の一覧（5 行/秒で状態が変わる）、流れ続けるログ（50 行/秒、上限 2,000 行）、2 万点のグラフ（10 点/秒）を、1280×800 の窓に並べます。中身は `Sources/Scenario.swift` で、`bench/src/scenario.js` と同じ値になります。

| 版 | 作り方 |
|---|---|
| `kodou` | KodouUI（`swift/`）。タイマーは 1 本、一覧とログは NSTableView で見えている行だけ、グラフは Canvas で描く幅の 1 列に 1 本 |
| `lazy` | `kodou` の一覧とログだけを SwiftUI の `ScrollView`＋`LazyVStack` にした版。行ごとに観測し、タイマー・リングバッファ・グラフは `kodou` と同じ |
| `tuned` | 手当てをした SwiftUI（Web の react-tuned に当たる）。SwiftUI の普通の範囲でよく勧められる手当てだけを入れ、AppKit は使わない。入れた手当ては下の「tuned に入れた手当て」 |
| `plain` | よくある書き方の SwiftUI。一覧は `List(selection:)`、ログは `ScrollView`＋`LazyVStack`＋`scrollTo`、グラフは Swift Charts の `LineMark` に全点。流れごとに `Timer` を 1 本ずつ |
| `web` | Web のベンチの Kodou-ui 版（`bench/dist/kodou.html`）を WKWebView で出したもの |
| `empty` | 地の色だけの窓。測る仕組みそのものの重さを見るため |

### tuned に入れた手当て

1. `@Observable` を行ごとに分け（`RowBox`）、変わった行だけが描き直されるようにする
2. `List` の行は Equatable な View にして `.equatable()` を付け、id は行番号で固定する
3. ログの追記は溜めておき、50ms ごとにまとめて配列へ反映する。末尾の追従は `defaultScrollAnchor(.bottom)` に任せ、`scrollTo` を呼ばない
4. Swift Charts に渡す点は、描く幅の 1 列に最小と最大の 2 点まで間引く（1,200 列、react-tuned の `decimate` と同じ）
5. タイマーは `.task` の中の 1 本のループにまとめ、窓が見えていないあいだ（`occlusionState`）は止める

## 回し方

```sh
bench/build.sh             # 先に Web のベンチを作る（web の版が bench/dist/kodou.html を使う）
python3 bench/swift/run.py # 3 回ずつ、流す時間は 60 秒。--stream 秒 と --only kodou,web で変えられる
```

Xcode は要りません。`bench/swift/build.sh` が `swift/build.sh` で KodouUI を作り、`swiftc` でベンチを `build/KodouBench.app` に包みます。

回しているあいだ、窓が手前に浮いて出ます。ほかの窓の下に隠れると止まる版があるためです。版ごとに 1 回およそ 85 秒かかり、3 回で 20 分ほどです。

## 測っているもの

1 回ごとに、窓を出してから 5 秒待ち、60 秒流し、選ぶ操作を 20 回して、最後に窓を画面から外して 10 秒待ちます。

| 項目 | 測り方 |
|---|---|
| メモリ | `footprint` コマンドの phys_footprint。選ぶ操作のあとに取る。`web` はアプリに加えて、そのとき増えた WebKit のプロセス（WebContent・GPU・Networking）を足す |
| 流している間の忙しさ | 60 秒のあいだに使った CPU 時間を `ps` で取り、60 秒で割る。1 コア分を 100% とする。`web` は WebKit のプロセスも足す |
| p95 フレーム・長いフレーム | ネイティブの版は、窓に付けた CADisplayLink が呼ばれる間隔。`web` は頁の中の requestAnimationFrame の間隔。p95 は遅い方から 5% の中央値、長いフレームは 50ms を超えた回数 |
| 選ぶ操作 | 行を選んでから、表示の更新が 2 回来るまでの時間。20 回の中央値 |
| 起動 | プロセスが始まってから、最初の表示の更新が 2 回来るまで。`web` は頁の `__ready` の時刻 |
| 隠れている間の忙しさ | 窓を画面から外して 10 秒のあいだの CPU |

## 結果（2026-11-26、Apple M6、macOS 27.0、3 回の中央値、流す時間 60 秒）

| | kodou | lazy | tuned | plain | web | empty |
|---|---|---|---|---|---|---|
| メモリ | 34 MB | 81 MB | 112 MB | 206 MB | 121 MB | 18 MB |
| 流している間の忙しさ | 7.3% | 30.0% | 37.1% | 100% | 19.7% | 0.4% |
| p95 フレーム | 13.3 ms | 13.3 ms | 44.9 ms | 228 ms | 15 ms | 13.3 ms |
| 50ms を超えたフレーム（60 秒） | 0 | 0 | 21 | 429 | 0 | 0 |
| 選ぶ操作 | 27 ms | 40 ms | 27 ms | 354 ms | 27 ms | 27 ms |
| 起動 | 146 ms | 151 ms | 196 ms | 703 ms | 254 ms | 112 ms |
| 隠れている間の忙しさ | 0% | 0% | 0.1% | 100% | 0.2% | 0% |

この Mac の画面は 75Hz なので、何も遅れなければフレームは 13.3 ms です。`web` のメモリ 121 MB の内訳は、アプリ 26 MB、WebContent 49 MB、WebKit の GPU 42 MB、Networking 5.5 MB です。1 回ごとの値は `results-2026-11-26.json` の `raw` にあります。3 回の差は、忙しさが `web` で 4.6 ポイント、ほかは 3 ポイント以内、メモリは 12 MB 以内でした。`web` の忙しさは、同じ日の先の測定（版を 5 つで回したとき）では 26.7% で、回すたびに 20〜27% の幅で変わります。

### tuned で何が効いたか

手当てを 1 つずつ外して、1 回ずつ測りました（60 秒）。

| | メモリ | 忙しさ | 50ms を超えたフレーム | 隠れている間 |
|---|---|---|---|---|
| tuned（全部入り、3 回の中央値） | 112 MB | 37.1% | 21 | 0.1% |
| グラフの間引きを外す（2 万点を渡す） | 190 MB | 100% | 372 | 0.1% |
| ログを 20ms ごとに 1 行ずつ反映する | 106 MB | 40.7% | 19 | 0.1% |
| plain（手当てなし） | 206 MB | 100% | 429 | 100% |

- いちばん効いたのはグラフの間引きです。外すと、ほかの手当てが入っていても 1 コアを使い切ります。
- ログをまとめて反映する効果は 3〜4 ポイントでした。
- 隠れている間の 100% が 0.1% になったのは、窓が見えていないあいだループを止める手当てです。
- それでも tuned は、50ms を超えるフレームが 60 秒に 21 回残りました。どこで止まっているかは切り分けていません。たぶん 100ms ごとのグラフ（2,400 点）の描き直しです。

### plain が隠れても 100% のままの理由

1 回ずつ、条件を 1 つだけ変えて測りました。

| | 流している間 | 隠れている間 |
|---|---|---|
| plain | 100% | 100% |
| Swift Charts を外す（`PLAIN_NO_CHART=1`、20 秒） | 100% | 100% |
| 窓が見えていないあいだ Timer を止める（`PLAIN_PAUSE_HIDDEN=1`、10 秒） | 100% | 0% |

Swift Charts を外しても 100% のままで、Timer を止めると 0% になりました。窓が見えていなくても Timer が配列を書き換え続け、そのたびに起きる SwiftUI の更新（`List` の 1 万行とログの 2,000 行）が原因です。その中のどこに時間がかかっているかまでは見ていません。Swift Charts は、見えている間の重さの一因ではあっても（tuned で間引きを外すと 100% になる）、隠れている間の 100% の原因ではありません。

### kodou のログを軽くした前後

`kodou` の忙しさのほとんどはログ（50 行/秒）でした。ログの更新を止めると 1.5% まで下がります（グラフを止めても変わりません）。そこで次の 2 つを入れました。

- 上限（2,000 行）で回ったあとは、見えている行を全部描き直すのをやめ、先頭の行を消して末尾に足す形で NSTableView に伝える
- 描き直しを `KodouTicker` の `frame(key, after:)` でまとめ、`batchMs`（既定 50ms）に 1 回にする

| | 忙しさ |
|---|---|
| 前（行ごとに描き直し、20ms ごとに反映。3 回の中央値） | 16.6% |
| 先頭を消して末尾に足す形だけ（1 回） | 15.4% |
| ＋ 16ms（1 フレーム）ごとにまとめる（1 回） | 13.0% |
| ＋ 50ms ごとにまとめる（1 回） | 8.8% |
| 後（50ms ごと。上の表、3 回の中央値） | 7.3% |

ログは 1 秒に 20 回描き変わります。読める速さより速く流れるログなので、20 回で足りると判断しました。Web の Kodou-ui のログは、表示の更新（requestAnimationFrame）ごとに描き変えています。`KodouLog.batchMs` で変えられます。

### そのほか

- `lazy` は、選ぶ操作で 1 万行の中を飛び回ったあとにメモリが 41 MB から 81 MB に増えました。`LazyVStack` が一度作った行を手放していないためだと考えていますが、確かめてはいません。この比較から、KodouUI の一覧とログは NSTableView にしました。
- `kodou` の行の文字は、文字と色ごとに組んだもの（CTLine）を使い回して、描く手間を減らしています。
- `web` は、同じ Kodou-ui の頁をネイティブの窓で出すと、メモリは `kodou` の 3.6 倍、忙しさは 2.7 倍でした。

## この数字が言えること、言えないこと

言えること:

- この Mac のこの場面では、Kodou-ui の決まり（見えている分だけ描く、タイマーは 1 本、隠れたら止める、点を描く幅まで間引く）を Swift に移すと、手当てをした SwiftUI より軽く、同じ頁を WKWebView で出すよりも軽い。
- SwiftUI だけで手当てをしても、1 万行の一覧と 50 行/秒のログでは、NSTableView で作った版の約 5 倍の CPU を使う。
- 一覧とログには、`LazyVStack` より NSTableView の方が、メモリも CPU も少ない。

言えないこと:

- Web のベンチ（`bench/README.md`）の数字とは比べられません。Web のベンチは画面に出さない headless の Chrome で、こちらは実際の窓に描いています。描く仕事の量が違います。
- フレームの数字は、メインスレッドが表示の更新に間に合ったかを見ているだけです。Instruments が使えない（Xcode が無い）ため、Core Animation と WindowServer が実際に画面へ出したコマ数は測れていません。`web` だけは WebContent の中の requestAnimationFrame で測っているので、ほかの版と測っている場所が違います。
- 忙しさは `ps` の CPU 時間（1/100 秒の単位）から出しています。WindowServer が合成に使った CPU は、どの版にも入っていません。
- `tuned` の手当ては、SwiftUI でよく勧められるものから選んだ 1 つの組み合わせです。ほかの手当て（グラフの更新を間引く、`List` を使わない等）で変わる余地があります。手当てを外した比べ方と、`plain` の切り分けは 1 回ずつで、3 回の中央値ではありません。
- 1 台の Mac（Apple M6、75Hz の画面）だけの結果です。
