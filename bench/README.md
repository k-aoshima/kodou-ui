# 省メモリの比較

Kodou-ui の「速さと軽さ」の決まりで作った画面が、React で作った同じ画面と比べてどれだけ軽いかを測る。macOS のネイティブ（SwiftUI・AppKit）で同じ画面を比べた結果は [swift/README.md](swift/README.md) にある。

## 比べる 3 つの版

どの版も同じ画面を出す。中身は `src/scenario.js` で共通にしている。

- 一覧: 10,000 行。1 行の状態が 0.2 秒ごとに変わる
- ログ: 0.02 秒ごとに 1 行増える。残すのは 2,000 行まで（どの版も同じ上限）
- グラフ: 20,000 点。0.1 秒ごとに 1 点増え、いちばん古い点を捨てる

| 版 | 作り方 |
|---|---|
| kodou | Kodou-ui の決まり。依存なし、rAF 1 本、変わった行だけ書き換え、一覧は見える行だけ、グラフは canvas で描く幅の 1 列に 1 本、隠れたら止める（`src/kodou.js`） |
| react-tuned | React 19＋MUI 9＋Recharts 3 に、よく勧められる手当てをしたもの。react-window で一覧とログを見える行だけにし、行は memo、グラフの点は描く幅まで間引く |
| react-plain | 同じ部品のよくある作り方。MUI の Table に全行、Recharts に全点を渡す |

## 測り方

```
npm install
./build.sh                 # dist に 3 つの版を出す
node run.mjs 3             # 3 回ずつ測って中央値を results-<日付>.json に書く
node run.mjs 3 --cpu 4     # CPU を 4 分の 1 の速さにして測る（遅い PC の代わり）
node run.mjs 1 --soak 5    # 流す時間を 5 分にのばし、最初と最後の JS のヒープを比べる
```

headless Chrome（1280×800）で開き、5 秒待ってから次を測る。

- ページの使用メモリ: レンダラのプロセスの footprint（macOS）。ガベージコレクションのあと
- JS のヒープと要素の数: Chrome の Performance.getMetrics
- 流している間の忙しさ: 20 秒のうち、メインスレッドが仕事をしていた割合
- 選ぶ操作: 一覧の行を選んでから 2 コマ描き終わるまで（20 回の中央値）
- 隠れている間の忙しさ: 別のタブを前に出してからの 10 秒

## 結果（2026-11-24、Chrome 158、Apple M6、3 回の中央値）

kodou の欄は、ログも見えている行だけ描くようにしたあとの値。かっこ内は直す前（ログの 2,000 行を全部要素にしていた版）の値。

| | kodou | react-tuned | react-plain |
|---|---|---|---|
| ページの使用メモリ | **57 MB**（86） | 128 MB | 733 MB |
| JS のヒープ | **1.8 MB**（1.7） | 28.2 MB | 287 MB |
| JS の大きさ（縮めたあと） | **6 KB**（5） | 817 KB | 817 KB |
| 表示まで | **23 ms**（37） | 82 ms | 467 ms |
| 流している間の忙しさ | **5.9%**（16） | 33% | 100% |
| うち JS | **1.4%**（1.5） | 29% | 97% |
| 1 コマの時間（遅いほうから 5%） | 16.8 ms | 16.8 ms | 233 ms |
| 選ぶ操作 | 33 ms | 34 ms | 398 ms |
| 隠れている間の忙しさ | **0.1%**（0.3） | 35% | 100% |
| 要素の数 | **470**（9,373） | 594 | 90,741 |

3 回のばらつきは、使用メモリで ±3 MB 以内だった。

## 読み方

- 手当てをした React と比べて、ページの使用メモリは半分以下（128 → 57 MB）、JS のヒープは 15 分の 1 だった。ヒープの差はフレームワークと部品の分で、「依存なし」の効き目が大きい。
- 最初に測ったとき、要素の数だけは kodou が負けた（9,373 対 594）。ログの 2,000 行を全部要素にしていたため。ログも見えている行だけ描くようにすると、要素は 470、使用メモリは 86 → 57 MB、流している間の忙しさは 16% → 5.9% に下がった。要素の数を減らすことが、使用メモリにも描画の重さにも効く。この結果から、数が決まっていない集まりはすべて見えている分だけ描く、を決まりにした（`docs/principles.md`）。
- 隠れている間に止まるのは kodou だけだった。ただし headless では setInterval が間引かれないので、ふつうのブラウザなら react-tuned の 35% はもっと小さくなるはず。
- 選ぶ操作の 33 ms は 2 コマ分で、この測り方の下限。kodou と react-tuned の差は、この方法では出ない。

## この数字が言えること、言えないこと

上の表は、次の条件での値である。ほかの条件にそのまま当てはまるとは限らない。

- file:// で開いた headless Chrome で、回線を通していない。Web フォントも読まない
- 画面は1つのシナリオだけ（一覧・ログ・グラフ）
- メモリの値は Chrome の版と測り方で変わる。同じ方法で測った版どうしの比べ合いとして読む

## 条件を変えた結果（2026-11-25、Chrome 158）

CPU を 4 分の 1 の速さにした結果（3 回の中央値）と、流す時間を 5 分にした結果（1 回）。

| | kodou | react-tuned | react-plain |
|---|---|---|---|
| ページの使用メモリ（CPU 1/4） | 55 MB | 127 MB | 590 MB |
| 流している間の忙しさ（CPU 1/4） | 1.9% | 54% | 100% |
| 1 コマの時間、遅いほうから 5%（CPU 1/4） | 16.8 ms | 16.8 ms | 817 ms |
| 選ぶ操作（CPU 1/4） | 33 ms | 34 ms | 1,562 ms |
| ページの使用メモリ（5 分） | 54 MB | 126 MB | 766 MB |
| 5 分で増えた JS のヒープ | 0.1 MB | 4.7 MB | 13.5 MB |
| 流している間の忙しさ（5 分） | 4.6% | 34% | 100% |

- CPU を遅くしても、kodou と react-tuned は 1 コマの時間と選ぶ操作が変わらなかった。react-tuned は忙しさが 33% から 54% に上がり、余裕が減った。
- kodou の忙しさは、CPU を遅くすると 5.9% から 1.9% に下がった。遅くすると忙しさが下がる理由は確かめていないので、この値は比べる材料に使わない。
- 5 分流しても kodou の JS のヒープはほぼ増えなかった（0.1 MB）。react-tuned は 4.7 MB 増えた。漏れているかどうかは、もっと長く流さないと分からない。
