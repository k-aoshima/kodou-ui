# パターン

場面ごとの決まり。どれも人の認知や使いやすさの研究を根拠にしていて、詳しくは `docs/research/retro-vs-modern.md` にある。

## 入力が主役の画面

- 検索ボタンや「適用」ボタンを置かない。1文字ごとに結果を描き変える。
- 小さな文法で組み合わせる。接頭辞の記号1つで絞り込みに入り（例: `#`、Vim の `:`）、条件はつなげて書ける（`#kind pdf #date 先月`）。名前は既に知られた定番（シェル、find/fd、Spotlight、Vim）に合わせる。ほかの道具とぶつかる記号は避ける。
- 確定した条件は入力欄の中でチップにし、消す・直すが1キーでできるようにする。
- CLI の弱点は「何が打てるか分からない」こと。入力欄が空のときや接頭辞だけ打ったときに、打てるものを一覧で見せる。
- 前に選んだもの、よく使う組み合わせを上に出し、名前を付けて保存できるようにする。2回目からは打つ量が減る。
- 選んだ行の中身は横か下にプレビューする。

## 状態の置き場所

- 今のモード、件数、メモリ、ブランチ、最後に起きたことは、下か上のステータスライン1本にまとめる。ダイアログで割り込まない。
- 1行に名前・種類・場所・時刻を並べ、余白で薄めない。数字や識別子は等幅で桁をそろえる。

## 確認と取り消し

- 取り消せる操作は、確認を出さずにすぐ実行し、トーストで「取り消し」を出す。
- 確認は、取り返しのつかない操作（削除、強制 push、プロセスの停止など）だけにする。確認は2回目から慣れて読まれなくなるため、乱発すると本当に危ないときにも読まれない。
- 確認はまずその場の1行で聞く: `spike/agent-steer を削除しますか [y/N]`。画面を止めるダイアログは最後の手段にする。
- 既定は安全な側にする（`y/N` の N、ボタンなら「やめる」）。
- 何が消えて戻せないのかを具体的に書く（「リモートにまだ送っていないコミットが2件あり、削除すると戻せません」）。

## 待ち時間

| かかる時間 | 見せ方 |
|---|---|
| 1秒未満 | 何も出さない。スピナーはちらつくだけになる |
| 1〜10秒 | スピナーに、何をしているかと件数か経過時間を添える |
| 10秒超 | 進捗バーで件数か割合、かかった時間、今の対象を出す |

- 進捗は実際の値で出す。終わりに向けて速く見せるような細工はしない（中が見えるの原則とぶつかる）。
- 入力への応答そのものは 0.1 秒以内（目標は 16ms）に返す。重い処理は後ろに回し、出せる分を先に描く。

## エラー

- 何が起きたかと、どう直すかを文で書く。「エラーが発生しました」だけで済ませない。
- エラーコードや生のログは消さずに、`<details>` で折りたたんで残す。調べる人には必要。
- 入力のエラーは、送る前に、打つたびにその欄の下に出す。
- 種類は色だけでなく `[FAIL]` のような文字でも示す。

## 文と等幅

- 文として読むところ（説明、確認の問い、AI の発言、エラーの説明）は プロポーショナル体（IBM Plex Sans JP、`--font-read`）で組む。和文と欧文が同じ系列で、技術者向けの硬さが等幅の格子となじむため。
- 等幅（`--font`）は、コマンド、データ、表、ログ、格子のように桁をそろえる所だけに使う。欧文 JetBrains Mono と和文 BIZ UDゴシックの組み合わせは、和文1字が欧文2字の幅に収まる。
- 本文は 15px 以上、行間は 1.75〜1.85、1行は和文で 35〜40字（`--measure: 38em`）までにする。表とログは幅いっぱいに使ってよい。
- 全部大文字は `NORMAL` `[INFO]` のような短い状態の語だけにする。

## 色

- 状態を色だけで伝えない。記号か文字を必ず添える（`[  OK  ]`、▲、「注意」）。
- グラフの系列は、色に加えて線の種類、点の形、ラベルで分ける。
- 読ませる文字は地に対して 4.5:1 以上、部品の境界とフォーカスは 3:1 以上。薄い色（`--deco`）は飾りだけに使う。
- 赤と緑は色相を CUD 寄りにし、明るさにも差をつける。
- 明るい地を標準にし、暗い地は選べるようにする。

## キーの学習

- メニューやツールチップにキーを書く。ただし、ショートカットの表示を目立たせるだけでは学習は進まない。
- ⌥ を押している間だけ、画面の部品の上に使えるキーの札を重ねて見せる。札は押したときに作り、離したら消す。ステータスラインで「⌥ を押すとキーが出ます」と案内する。
- 配置と並び順を変えない。同じ入力には同じ結果を同じ順で返す。
- 機械の解釈を見せて、機械の言葉を覚えられるようにする（「ブランチ」と打ったら `#kind:branch` のチップにして、次からはこう打てると出す）。

## 速さと軽さ

道具は一日中開いたままなので、待たせず、メモリを食わせない。

- **依存を持たない**: ライブラリを使わない。状態の見た目はできるだけ CSS で出す（`:hover` `:focus-visible` `:has` `:checked` `:user-invalid`、`details`、`popover` 属性、`<dialog>`）。
- **イベントは委譲**: 部品の親で1つだけ受ける。
- **差分だけ更新**: 一覧は全体を `innerHTML` で作り直さず、変わった行だけ差し替える。並べ替えは行の要素を動かす。
- **仮想スクロール**: 長い一覧は見えている行だけを描き、行の要素を使い回す。
- **リングバッファ**: 流れ続けるデータは上限を決め、古いものから捨てる。
- **描画の範囲を絞る**: 画面外の節に `content-visibility: auto` と `contain-intrinsic-size`、部品の中身に `contain: content`。
- **動きは transform と opacity だけ**: 読み取りと書き込みは `requestAnimationFrame` でまとめる。
- **間引く**: グラフの点は描く幅のピクセル数まで減らす（列ごとに最小と最大を残す）。点が多いものは canvas で描く。
- **隠れたら止める**: 頁が隠れている間（`visibilitychange`）と画面外（`IntersectionObserver`）では、タイマーとアニメーションを止める。タイマーは `requestAnimationFrame` の1本にまとめる。
- **測って見せる**: キー入力から描画までの時間（`performance.now` と `requestAnimationFrame`）、要素の数、JS ヒープ（`performance.memory` がある時だけ）を画面に出す。目標はキー入力から描画まで 16ms 以内。

見本帳を headless Chrome で測った値（2026-11-23）は、要素の数 1,782、JS ヒープ 9.5 MB、2万点のグラフを 831 列に間引いて描画 0.5ms だった。キー入力から描画までの時間は headless では測れていない。
